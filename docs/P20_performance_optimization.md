# Phase 16: Performance Optimization Guide

This guide details strategies for optimizing both the migration process itself and the performance of the generated Databricks Lakeview dashboards.

## 1. Dashboard Performance (Post-Migration)

Lakeview dashboards perform best when the underlying data is optimized for Databricks SQL. Direct 1:1 translation from Tableau extracts might yield sub-optimal performance on Lakeview if Databricks-specific optimizations aren't applied.

### 1.1 Dataset Deduplication
- **The Problem**: Tableau workbooks often define multiple identical or near-identical data sources for different worksheets.
- **The Optimization**: The migration engine analyzes the ASTs of all generated queries. Identical queries are merged into a single Lakeview `dataset`. Multiple visualization widgets can reference the same dataset, drastically reducing the number of concurrent queries sent to the SQL Warehouse upon dashboard load.

### 1.2 Query Optimization (Pushdown)
- Ensure all aggregations (`SUM`, `COUNT`, `AVG`) are pushed down into the dataset query rather than calculated on the client side.
- Limit the columns retrieved to only those used in the visualizations or cross-filters.

### 1.3 Materialized Views (MVs)
- **Recommendation**: For highly complex Tableau data sources with multiple joins (e.g., star schemas), recommend the creation of Materialized Views in Unity Catalog.
- The migration tool will tag complex SQL statements in the audit report, suggesting them as candidates for MV creation.

### 1.4 Warehouse Selection
- **Serverless SQL Warehouses** are strongly recommended for Lakeview dashboards due to their near-instant start times and dynamic scaling, which perfectly suit bursty dashboard viewing patterns.
- Ensure the warehouse is appropriately sized (e.g., Small vs Large) based on the concurrency expectations.

## 2. Migration Pipeline Performance

Migrating thousands of workbooks requires an optimized processing pipeline.

### 2.1 Parallel Processing
- **Parsing**: `xml.etree.ElementTree` is used for parsing `.twb` files. Parsing multiple independent files can be parallelized using Python's `multiprocessing` pool or `concurrent.futures.ProcessPoolExecutor`.
- **LLM Calls**: Make asynchronous calls to LLM APIs using `asyncio` and `aiohttp` to prevent I/O blocking during fallback translations.

### 2.2 Batch API Calls
- When creating resources in Databricks via the REST API (if deploying automatically), batch operations where possible or use asynchronous requests to avoid blocking on network latency.
- Connection pooling is enabled by default in the Databricks SDK.

### 2.3 Resource Profiling
- Use `cProfile` and memory profilers during the development of the parsing engine to ensure XML traversal does not cause memory bloat on exceptionally large (100MB+) `.twb` files.

## 3. Query Optimization for Databricks (Data Level)

The migration tool provides recommendations for the underlying Delta tables to ensure the generated dashboard queries run efficiently.

### 3.1 Partition Pruning
- If the Tableau dashboard relies heavily on a date filter (e.g., `Order Date`), the migration report advises partitioning the underlying Delta table by that date column to leverage partition pruning.

### 3.2 Z-Ordering
- For highly granular filtering on high-cardinality columns (e.g., `Customer_ID`, `Product_SKU`), recommend running `OPTIMIZE table_name ZORDER BY (Customer_ID)`.

### 3.3 Statistics Collection
- Run `ANALYZE TABLE table_name COMPUTE STATISTICS` to ensure the Databricks Cost-Based Optimizer (CBO) has accurate metadata for the queries generated by the dashboard.

### 3.4 Photon Engine and AQE
- Ensure that the SQL Warehouses used for the dashboard have the Photon engine enabled for vectorized query execution.
- Adaptive Query Execution (AQE) is enabled by default in Databricks, which handles dynamic partition coalescing and skew remediation automatically.

## 4. Large Dashboard Optimization Guidelines

Tableau allows for highly dense dashboards. Lakeview has different rendering paradigms. The migration tool enforces or recommends structural changes for massive dashboards.

### 4.1 Widget Count Limits
- **Recommendation**: Maximum 15-20 widgets per dashboard tab.
- **Migration Action**: If a Tableau dashboard contains >20 worksheets, the tool issues a warning and suggests splitting the dashboard into multiple tabs or pages.

### 4.2 Dataset Count Limits
- **Recommendation**: Consolidate to < 5 datasets per dashboard where possible.
- **Migration Action**: Deduplication (see 1.1) is aggressively applied.

### 4.3 Cross-Filter Performance
- Lakeview supports cross-filtering. However, enabling it across many dense visualizations triggers multiple queries on interaction.
- **Recommendation**: Limit cross-filtering to top-level aggregate KPIs or simple categorical bar charts. Avoid enabling it on dense scatter plots or massive tables.
